# Legacy World Transition Decision

Accepted 2026-08-10. The legacy hand-authored world remains supported while
the generated reconstruction is built beside it. Inventory of what exists:
[legacy_city17_inventory.md](legacy_city17_inventory.md). Generation rules:
[territory_generation.md](territory_generation.md).

## Decision

Two worlds coexist during transition. The legacy map is not migrated wholesale.

- Legacy `City17_Persistent_WP` stays as the existing playable entry until
  the generated territory reaches parity.
- The generated `kazan_territory_v1` world grows beside it, filled
  consistently as each layer is admitted, and becomes the new entry when it
  is ready.

Once the generated experience passes its load/package gate, the menu exposes
one explicit entry for City17 and one explicit entry for the generated world.
The widget requests logical experience IDs; it never owns map package paths.
No generic world browser or dynamic catalog is required for two entries.

The game already
boots to `MainMenuWorld`, not to the legacy map (`EditorStartupMap` points at
the legacy map, `GameDefaultMap` does not), so this requires no
default-entry-point surgery.

## Why not migrate

The legacy map holds 2,528 individually placed StaticMeshActors, 7
InstancedFoliageActors, 203 ObjectDefinitions, a Landscape, and 7 Data
Layers. Hand-migrating that produces content the regeneration contract
cannot reason about: placements with no canonical anchor, no owning scope,
and no way to prove they survived a rebuild. The territory doc's delivery
stage 3 already forbids migrating legacy buildings, trees, or props into
the generated base; this record is that rule applied to the whole map.

## Rules while both exist

1. The legacy world is FROZEN for new work. Bug fixes only. Adding features
   to both worlds costs twice and delays the transition indefinitely.
2. ALL new hand-authored work goes into the generated world's authored
   overlay, anchored per the territory doc's anchor semantics, from the
   first object. Raw placement is not acceptable there - an unanchored
   object cannot be proven to survive regeneration.
3. Retirement follows the milestone's content-integration slice, per class,
   never as a bulk move.

## Per-class disposition

| Legacy content | Disposition |
|---|---|
| Placed static meshes bound to geography | Regenerate from canonical records or retire; never migrate |
| Foliage / InstancedFoliageActors | Regenerate from canonical vegetation records |
| Landscape | Regenerated by the territory pipeline |
| Hero locations and gameplay landmarks | Migrate as coordinate-anchored protected overlay entries |
| Reusable art kits | Feed the procedural building route after a licensing audit and a measured prototype |
| Data Layers | Re-created as authored/generated separation in the new world; not copied |
| Anything with unclear licensing or hidden map dependencies | Exclude |

## Retirement condition

The legacy world is removed only after the generated world carries an
accepted playable scenario, every retained reference has moved,
repository-wide reference checks find no required dependency on it, and
build/tests/package pass without it. One pass, no compatibility alias, no
dual authority.
