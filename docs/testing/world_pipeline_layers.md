# World Pipeline Test Layers

This is the test-selection SOT for world reconstruction work. Use the lowest
layer that proves the current change, then advance only when crossing that
layer's boundary. Packaging is a release proof, not an inner-loop test.

**Never rerun a higher gate merely because another edit occurred. Select it
only when the changed dependency can alter the output or acceptance property
that gate proves. Reuse an accepted receipt only while those authenticated
inputs and that property remain unchanged.**

When a gate fails, identify its first failing owner from the receipt or log.
Fix and rerun that owner's smallest check in the current checkout or a small
fixture. A failed downstream step does not invalidate accepted upstream evidence
unless its authenticated inputs or acceptance property changed. Do not create a
new full release worktree, rebuild unrelated targets, or regenerate territories
as the debugging loop for a mirror, payload, or other downstream failure.

| Layer | Purpose | Data scope | Required proof | Explicitly excluded |
|---|---|---|---|---|
| L0 Edit | One logic or contract change | Scratch data or read-only fixture | Exact Python/Pester test, schema check, or exact UE automation test | Persistent world mutation, Kazan, package |
| L1 Fixture | Cross-component behavior | Transient outputs plus `ProjectWorldTestData` | Targeted synthetic source/compile/realization proof with rollback | Production data, durable promotion, package |
| L2 Slice | Exit an implementation slice | Affected territory validation profile or read-only production runtime | Producing changes: common Check plus affected Matrix; runtime changes: focused uncooked gameplay admission | Durable enrollment, package, packaged performance |
| L3 Promote | Replace persistent generated authority | Owning data plugin only | Accepted Matrix evidence, explicit enrollment, read-only authority audit | Package unless the slice changed a release boundary |
| L4 Release | Prove the shipping artifact | `ProjectWorldData` production map | Final `accept`: package, IoStore, packaged render/performance, post-audit | Routine iteration |

L0, L1, and L2 never leave durable generated-world mutation behind. Matrix may
regenerate real UE packages inside its locked transaction, but it restores the
exact pre-run path/hash set before returning. L3 is the first layer allowed to
persist generated packages or manifest authority.

## Fresh-Agent Route

1. Run `python -S tools/World/EndToEndValidation/bootstrap.py plan --base
   <slice-base>` to classify changed paths. Use `HEAD` for uncommitted work or
   the commit before the slice after changes were committed.
2. Run L0 while editing. Add L1 only for a cross-component or Unreal fixture
   boundary.
3. At a World-producing slice exit, run the L2 gates selected by `plan`.
   Reuse one current common Check receipt for every required Matrix; do not
   repeat common suites per Matrix. Use the Matrix mode printed by `plan`:
   `canonical_authority` for a World-only change, `full` when source or
   canonical owners changed. For a release wrapper, mirror, payload, or docs
   change that does not alter World production, use its owning focused checks;
   do not add a World Matrix by association.
4. Run L3 only when accepted generated bytes or manifests must change.
5. Run L4 only when the operator requests packaging or during authorized release
   preparation. If packaged behavior still needs proof outside those tasks,
   report that gap; do not silently start a package build. A code edit alone
   does not require recooking unchanged content or rebuilding Shipping.

The `canonical_authority` territory Matrix starts from the current promoted
bundle. It validates that bundle and its current external input files, then
proves World Apply, no-op, road locality, rejected Apply, reconstruction, and
exact restoration. Pass `--from-canonical-authority --changed-base <slice-base>`
to `run`. Its receipt does not claim a fresh source download, deterministic
recompile, or compiler incremental proof. The command refuses this mode when
the candidate changed path set contains SourceIngestion, CanonicalCompilation,
their execution environment, source/compiler profiles, controls, budgets, or
the canonical authority. Use the full Matrix for producing upstream changes.
The slice base must precede every unaccepted change in the candidate; `HEAD`
is valid for uncommitted work only when earlier committed changes have their
own accepted boundary. A multi-commit review records the complete path set
from its original base and separately identifies any earlier, proved
nonproducing upstream cleanup. A World-only Matrix after that boundary proves
only the later World candidate, not historical raw-source replay. An upstream
change whose effect is not proved remains a full-Matrix requirement. A missing
raw cache does not invalidate a verified promoted canonical
bundle, but it prevents full historical source replay until the exact pinned
bytes are recovered.
The World-only run does not inspect raw-cache size. Clean reconstruction
compares saved Mesh Terrain, Map, and Building Massing output after the Mesh
Partition builder. The projections cover compiled terrain geometry and
collision, presentation and partition state, and building mesh, material, and
collision. Only external actor paths in affected map/terrain scopes can move on
clean reconstruction; all other paths and all no-op/locality paths stay fixed.

| Changed boundary / available input | Decision | Proof or stop |
|---|---|---|
| World realization only; promoted canonical validates | Run `canonical_authority` Matrix, then the scoped L3 transaction if generated authority must change | World receipt and post-transaction authority audit |
| Earlier compiler cleanup already accepted as nonproducing; current candidate is World-only | Record the original review base, complete changed paths, cleanup proof, and accepted commit boundary; run `canonical_authority` only for the later candidate | The receipt does not prove a fresh compile for the complete history |
| Source ingestion or canonical compiler changed; exact pinned raw snapshot is cached or archived | Run `full` Matrix with the pinned source identity | Fresh ingestion and compile proofs before World acceptance |
| Source or compiler changed; exact pinned raw snapshot is absent | Recover the same pinned bytes from a verified mirror or provider, then run `full` | Stop if the exact revision and digest cannot be recovered; do not substitute another date |
| Promoted canonical fails validation | Diagnose the authority and its inputs before generation | Stop; neither a raw cache hit nor a World-only run repairs invalid authority |

The raw provider snapshot is the replay input; the ingestion cache is only a
local acceleration. The promoted canonical bundle is the durable input for
World-only development. Web retrieval is used only to recover a required
exact pinned snapshot for full replay, with its declared digest verified.

The End-to-End validation profile mixes World expectations with source and
compiler references. The planner compares its upstream fields with the slice
base: World expectation edits keep `canonical_authority`; source/compiler
reference or upstream budget edits select `full`. An unreadable base copy
selects `full`.

## Impact-Driven Development

### Uncooked gameplay admission

Before requesting a frozen release commit for changes that can alter the product
route, movement, collision, streaming, or playable driver, prove the affected
gameplay on the existing production maps without cooking or regeneration.
Changes shared by both product routes require both cities. The operational
command and receipt contract are owned by
[World runtime verification](../../scripts/ue/world/README.md#uncooked-gameplay-admission).
This read-only L2 route does not require a generation Matrix when no producer
output or consumed generation contract changed.

The probe reuses the real menu/loading route, possessed character, input driver,
collision, and cell-residency tracker. Uncooked results prove that envelope only;
they never certify packaged performance or cooked collision. Validate native
world/envelope identity and unchanged generated authority. A fixture containing
the right receipt fields cannot prove map geometry or physics.

After a late release failure, record the first failing owner/property, cheapest
permanent reproducer, invalidated evidence, and still-valid evidence in the
current task. Extract a cheaper real reproducer whenever the property exists at
a lower layer. Before rerunning release, show that it rejects the relevant bad
behavior, then accepts the fix and its materially affected controls. A different
startup error or synthetic receipt rejection is not that known-bad control.
Some failures depend on cooked or Shipping bytes; keep their cheapest exact
artifact probe instead of claiming an uncooked substitute covers them.

Release-debugging impact and frozen-source reuse rules are owned by
[release preparation](../../scripts/ue/package/README.md#preparation-preflight-and-failure-triage).

### Changed-owner selection

Classify the changed output before choosing a gate. Documentation and tests
need their focused checks. Runtime C++ needs an incremental affected-target
build and its exact runtime test; material parameters need an immediate visual
check; a texture algorithm needs its generation tests and runtime preview.
Mesh Terrain implementation needs affected geometry tests and targeted
realization. Canonical data changes need only the affected cells and dependent
layers unless a shared semantic or geometry producer genuinely changes all of
them. A material or validation-only edit must not invalidate geography.

World producer identity is the producer ID and output revision, shared
realization pipeline revision, engine build identity, and declared data-input
digests. Source edits alone do not move it. A behavior change that alters
generated output bumps the owning output revision, or the pipeline revision for
shared realization behavior, and records new verify baselines. The producer
verify compares saved output against its accepted baseline; common Check runs
the full verify suite. `plan` and the common-check staleness hash use the same
declared generation roots. If a formula change leaves only fingerprint currency
stale, use the documented identity refresh transaction after the verifies pass;
never edit manifests by hand to silence the audit.
Reuse cooked content only when its cooked inputs and required runtime route are
still valid. Full cross-city regression and Shipping packaging belong to the
release candidate or a specific property that narrower tests cannot prove.

Every black box is developed and tested on its own by default. An owner may
recompute when its own inputs or implementation change; its consumers rebuild
only when an input or public contract they actually consume changes
([Component Ownership](../architecture/principles.md#component-ownership)).
Each generated-content owner proves that locality in its own cheap tests: an
internal or provenance change leaves consumer identity unchanged, and a contract
change invalidates exactly its consumers. The default order is owner tests, the
owner's isolated fixture, a consumer's integration only when a contract it
consumes changed or a focused test found an integration failure, a targeted
Development runtime, then the release candidate. An expensive gate names the
changed dependency it authenticates: the owner's own producing input or a
producer's public contract. A change that unexpectedly needs another owner's
outputs regenerated, such as World for a texture or material edit, is
ARCHITECTURAL RED (see Change Locality), not a reason to run the larger gate.

`plan` is a read-only static path classifier. It selects possible gates but
never runs tests, mutates generated content, or decides artifact authority.
Its L3 candidate owners are selected only by generator changes or changed
generated packages/manifests. Human-authored source, control, and profile data
never imply promotion by themselves.

## Review Cadence

Use two deliberate review points per slice. They are named, and both are
performed by an INDEPENDENT reviewer:

| Gate | When | Scope |
|---|---|---|
| R1 | before production code | complete lifecycle: identities, owner, mutable inputs, current versus historical evidence, budgets, retry, rollback, concurrency |
| R2 | after focused L0/L1 tests pass | the integrated system once; fix a discovered defect class across the whole lifecycle before requesting the final affected L2 gate |

Independence is the invariant, not tooling: the reviewer must not have authored
the production change under review. A different model or tool is PREFERRED
because it decorrelates blind spots, but it is not mandatory - the operator
chooses the reviewer.

Reviewer inputs: the slice plan, its read-first SOTs, and the diff plus
evidence. Verdicts are `PASS`, `PATCH`, or `BLOCKER`. On `PATCH`, the
implementer makes the correction and the SAME independent reviewer may recheck
it; a brand-new reviewer per correction adds ceremony without adding
independence. The reviewer never authors the fix - doing so would make it the
author of the change it is reviewing, which is the one thing the R1/R2 contract
exists to prevent.

Do not alternate reviewer comments with Matrix runs. While code or contracts
are still changing, stay at L0/L1. A fresh Check and the planner-selected
Matrix runs happen once at the coherent slice boundary.

## Proof Traceability

Every slice plan carries ONE table binding what it intends to guarantee to what
actually proves it. Two unlinked lists - "required invariants" here, "proof
classes" there - is how an invariant reaches production with nothing measuring
it, and how a gate gets reported as broader than it is.

| Invariant | Acceptance surface | Execution envelope | Cheapest proof | Final proof | Stop condition |
|---|---|---|---|---|---|

Column meanings:

- **Invariant** - the property that must hold. One row each.
- **Acceptance surface** - the representation actually consumed at the boundary
  being accepted, never one of its inputs.
- **Execution envelope** - executable, editor vs commandlet, RHI/headless mode,
  flags, build configuration. Stated up front, not discovered after a failure.
- **Cheapest proof** - the smallest L0/L1 check that can falsify the invariant
  during iteration.
- **Final proof** - the evidence that authenticates the invariant at slice exit.
- **Stop condition** - what a failure of the final proof blocks.

Rules:

1. Every invariant has a final proof.
2. Every ACCEPTANCE proof maps to an invariant. A gate that answers to no
   stated invariant is either an undeclared requirement or wasted expense.
3. Diagnostic evidence MAY exist with no invariant, but only when labelled
   `DIAGNOSTIC / NON-AUTHORITATIVE`. It never gates anything. Keeping useful
   instruments from falsified hypotheses is correct; presenting one as
   acceptance is not.
4. An acceptance proof run in a materially different execution envelope does
   NOT authenticate the shipping envelope. Mark it diagnostic, or rerun it in
   the shipping envelope.

R1 rejects a plan that shows any of: an invariant with no final proof; an
acceptance proof that maps to no invariant; a wrong-envelope proof presented as
acceptance.

## Change Locality

For a substantial change, R1 also records four lines BEFORE coding:

```text
owning black box:
public interface / contract:
expected components CHANGED:
expected components UNTOUCHED:
```

If implementation then requires editing an owner listed as untouched, or
regenerating its outputs, that is ARCHITECTURAL RED: stop and review the
boundary before continuing. It is not
"just more implementation work" - it is the boundary telling you it is in the
wrong place, and it is far cheaper to hear that in R1 than after the change has
spread.

Worked example - adding a second road generator:

```text
owning black box:   road generator
contract:           generator registration + road profile
CHANGED:            road generator, registration, road profile, focused tests
UNTOUCHED:          terrain generator, water generator, transaction engine,
                    canonical ownership, active-set machinery
```

"To add this road type I also need to modify terrain, water, and the
transaction engine" is an R1 `PATCH`, not a progress report.

This is the testable form of open/closed for ALIS: it names, in advance, which
black boxes are expected to stay shut, so a violation is observable instead of
arguable.

## Ownership Boundary

- `ProjectWorld`: reusable schemas, C++/script logic, and tests. It contains no
  UE content packages and owns no concrete world-data manifests.
- `ProjectWorldTestData`: editor-only synthetic profiles, inputs, and authored
  fixtures. Generated packages and manifests are ignored transient L1/L2
  outputs; a clean checkout starts without TestData generated authority.
- `ProjectWorldData`: Kazan production profiles, authored content, baked
  generated packages, and their concrete manifests.

Test data is data even when it is generic. A fixture never moves into the
logic plugin merely because several tests reuse it.
