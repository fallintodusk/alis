**Verdict:** the best path for ALIS is **not** "collect photos, hand-rebuild in Blender, then import meshes." It is to turn ALIS's existing JSON-first architecture into a **world genome pipeline**: open geospatial data and raw earth sources become canonical tile data; Unreal's stock systems handle partitioning, streaming, and rendering; PCG, Geometry Script, and shape grammar turn that structured data into terrain, roads, buildings, and biome detail; and agentic tools operate on schemas, rules, and validation, not on raw mesh micromanagement. That direction matches the architecture already visible in the ALIS repo and aligns with the newest Unreal and agent tooling much better than a manual DCC-heavy workflow. [[1]](https://github.com/<user>/alis/blob/main/Plugins/Editor/ProjectDefinitionGenerator/README.md)

## What ALIS already gets right

ALIS already has the right philosophical core for a real-world open world. The repo describes a three-stage data pipeline where sync updates references, the generator performs one-way JSON-to-DataAsset transformation with validation, hashes, incremental regeneration, and orphan cleanup, and downstream tools propagate definition changes into scene actors. In other words, ALIS already treats `.uasset` files as generated engine-facing artifacts rather than the deepest source of truth, which is exactly the right foundation for large-scale procedural worlds. [[2]](https://github.com/<user>/alis/blob/main/Plugins/Editor/ProjectDefinitionGenerator/README.md)

The world side is also already pointed in the right direction. `ProjectWorld` explicitly says not to "fight" World Partition: Unreal owns the runtime grid and streaming cells, while ProjectWorld adds tile math, world-data loading, streaming hooks, and spatial queries on top. It also states that each tile should have one world-data source describing geometry, POIs, zones, events, and streaming hints, and that world plugins should own their JSON/DSL tile files and maps while `ProjectWorld` provides the tools. That is already extremely close to the right architecture for "real world in 3D." [[3]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

Just as important, the repo already encodes the correct limit for LLMs and agents: ALIS documentation says world JSON should **not** become a giant list of every chair, lamp, bush, or raw mesh transform. Instead, world data should answer **where**, **what type**, **how dense**, and **which preset**, while generators and PCG decide exact placement. It also says agents should edit structured vocabulary like `building_type`, `zone_type`, `density`, `damage_level`, and presets, not raw floating-point vertex heights or hand placement. That is the key design rule that makes an agentic world pipeline scalable instead of chaotic. [[4]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

The resource/plugin design also supports a "building DNA" model. `ProjectObject` describes actors as thin wrappers that compose reusable capability components, with the rule "Actor = Mesh + Capability Components." That means ALIS does not need "final handcrafted buildings" as the primary object unit. It can generate a building shell, facade modules, entrances, gameplay capabilities, and interaction metadata as composable parts, which is much closer to how a living procedural city should be built. [[5]](https://github.com/<user>/alis/blob/main/Plugins/Resources/ProjectObject/README.md)

## The strategic architecture ALIS should adopt

The big-picture architecture I recommend is a **four-layer world genome**.

The first layer is the **raw earth layer**: open terrain, vector map, and optional point-cloud or imagery sources stored as cloud-native geospatial assets. GeoParquet is an OGC-backed open format for vector geodata in Parquet; STAC standardizes geospatial asset catalogs; Cloud Optimized GeoTIFF is designed for HTTP range requests; GDAL is the core open-source translator/processing library for raster and vector formats; PDAL plays the equivalent role for point clouds; and DuckDB's spatial extension provides a lightweight SQL analysis layer over geospatial data. For ALIS, this layer belongs in MinIO or another object store, not inside Unreal. [[6]](https://geoparquet.org/)

The second layer is the **canonical ALIS world genome**: one versioned tile document per world tile, plus shared archetype libraries. This is where ALIS-specific JSON should live. I would keep this schema simpler than full GIS interchange formats, but make it rich enough to express tile bounds, CRS references, terrain source pointers, road centerlines, footprints, building archetype DNA, zoning, biome rules, event layers, gameplay tags, and deterministic seeds. CityJSON is worth supporting as an import/export bridge because it is an OGC standard for 3D city models and is explicitly JSON-based and programmer-friendly, but I would **not** make full CityJSON the internal core if it makes everyday game authoring heavier than necessary. ALIS should own a compact schema optimized for gameplay, then adapt out to standards when useful. [[7]](https://www.ogc.org/standards/cityjson/)

The third layer is the **Unreal realization layer**. World Partition should stay the stock partition/streaming system because Epic's system already stores the world as a persistent level subdivided into streamable grid cells loaded by streaming sources. On top of that, ALIS should use Landscape for terrain import, Georeferencing for CRS alignment, PCG for scattering and layout, Geometry Script for mesh generation/manipulation, Shape Grammar for modular building and facade logic, Nanite for dense static geometry, Runtime Virtual Texturing for landscape and spline blending, and builder commandlets for headless generation and rebuild. This lets ALIS lean on the engine where the engine is strongest. [[8]](https://dev.epicgames.com/documentation/unreal-engine/world-partition-in-unreal-engine)

The fourth layer is the **runtime stream layer**. The client should never need "the world" in one giant baked state. Instead, it should stream coarse tile metadata first, then terrain, then roads, then footprint-level building DNA, then local detail and point-of-interest overrides based on player proximity and relevance. That design follows World Partition directly, and it also matches ALIS's own distinction between tile/world data and exact actor realization. The result is that "infinite real world" becomes a controlled streaming problem, not a one-time bake problem. This is partly an inference, but it follows directly from Unreal's grid-stream model and ALIS's tile-driven world-data model. [[9]](https://dev.epicgames.com/documentation/unreal-engine/world-partition-in-unreal-engine)

This is also why the earlier Blender/Google-photo mental model should be retired. Google's Maps Platform terms explicitly prohibit scraping or bulk extraction of Maps content and also prohibit creating new content from Google Maps content, including tracing roadways or building outlines from satellite basemaps, creating 3D building models from imagery, or building terrain models from elevation content. So even before the workflow becomes too manual, it becomes a licensing trap for an open-source project. [[10]](https://cloud.google.com/maps-platform/terms)

## The open stack that fits ALIS best

For **terrain**, ALIS should use a "mother heightmap" strategy exactly like the ProjectWorld docs suggest: one continuous source surface, sliced to the world grid, with edits flowing back to the source rather than sculpting each tile in isolation. Unreal's landscape system supports 16-bit grayscale heightmap imports, including RAW with a separate JSON descriptor; UE 5.3 also improved large landscape import/export by leveraging World Partition for very large landscapes. The repo's own docs say the continuous heightmap should be the base truth, while tile streaming happens afterward. That is the correct terrain backbone. [[11]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

For **terrain source data**, the practical open baseline is Copernicus DEM, which provides global 30 m or 90 m coverage depending on area and availability. But Copernicus DEM is a **digital surface model**, meaning it includes buildings, infrastructure, and vegetation. So it is a good open baseline for regional shape, but not the final answer for dense urban ground truth. In cities or hero regions, ALIS should prefer local open DTM/LiDAR when available and process those sources with PDAL and GDAL. That recommendation is an inference from the Copernicus definition and from what PDAL/GDAL are designed to do. [[12]](https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM)

For **roads and footprints**, Overture Maps is the most interesting new industrial open source base. Its transportation theme is a global open dataset built from OpenStreetMap and enhanced with TomTom and other authoritative data sources, and its buildings theme aims for comprehensive worldwide building structures. Overture is distributed in GeoParquet, updated monthly on AWS, and licensed under CDLA-Permissive-2.0 except where ODbL-derived content requires ODbL treatment. OpenStreetMap remains essential underneath and is openly reusable under ODbL, but Overture gives ALIS a more normalized, industrial ingestion target. [[13]](https://docs.overturemaps.org/guides/transportation/)

For **roads in-engine**, ALIS should prefer vector centerlines plus parametric realization, not hand-authored road meshes. Unreal Landscape Splines can raise/lower terrain to match a spline with controlled falloff and optionally paint landscape layers at the same time. That makes roads a geometry-and-terrain coordination problem, which fits the ALIS "rules first, exact realization later" philosophy much better than full manual road modeling. [[14]](https://dev.epicgames.com/documentation/unreal-engine/landscape-splines-in-unreal-engine)

For **buildings**, the best big-picture move is to split them into three classes. First, "massing buildings" derived directly from footprints and height/class attributes. Second, "archetype buildings" generated from footprint plus building DNA using PCG and shape grammar, with facade modules, roof rules, stairs, doors, interior presets, damage, and style themes. Third, "hero buildings" that get special bespoke treatment, either hand-authored or reconstructed from owned imagery. Unreal's shape grammar system is specifically designed around modules and rules for procedural structure generation, and Geometry Script gives you Blueprint/Python-accessible mesh generation and editing when shape grammar alone is not enough. This is exactly where a "DNA grows organism" metaphor becomes technically useful rather than poetic. [[15]](https://dev.epicgames.com/documentation/unreal-engine/using-shape-grammar-with-pcg-in-unreal-engine)

For **detail generation**, Epic's PCG framework is the right default. PCG is already positioned by Epic for everything from building and biome utilities to entire worlds; it integrates with World Partition data layers; it has partitioned, hierarchical, and runtime generation modes for large worlds; and it now includes GPU processing options for suitable workflows. In ALIS terms, that means tile JSON should carry semantic intent and parameters, and the PCG graphs should own the last-mile realization of vegetation, clutter, facade variation, road-edge dressing, and micro-topography detail. [[16]](https://dev.epicgames.com/documentation/unreal-engine/procedural-content-generation-framework-in-unreal-engine)

For **automation and rebuilds**, Unreal's builder commandlets are a major enabler. World Partition provides batch commandlets for nav, foliage, PCG, and other builders, and the World Partition PCG Builder supports unattended runs, graph filtering, iterative cell loading, and memory-friendly processing of large worlds. That fits ALIS's backend and CI mindset much better than an artist-driven "open editor and click regenerate" loop. [[17]](https://dev.epicgames.com/documentation/unreal-engine/world-partition-builder-commandlet-reference)

For **optional globe-scale or preview geospatial integration**, Cesium for Unreal is the strongest open-source adapter worth evaluating. The project is Apache 2.0, free for commercial and non-commercial use, and explicitly designed to bring the 3D geospatial ecosystem into Unreal with support for physics, collisions, character interaction, and landscaping tools. My recommendation is to keep Cesium **optional** and **adapter-level**, not as ALIS's canonical world source. Use it for evaluation, preview, or special globe modes if needed, but keep ALIS's canonical source-of-truth in its own JSON/tile pipeline. [[18]](https://github.com/CesiumGS/cesium-unreal)

For **hero-zone reconstruction**, do not use Google imagery. If ALIS later wants unique landmarks or "scan-grade" special areas, the open path is owned or properly licensed imagery processed through tools like COLMAP and OpenMVS, optionally assisted by segmentation models like SAM/SAM 2. That lane should be reserved for exceptional areas where procedural massing is not enough, not for the default city-building pipeline. [[19]](https://cloud.google.com/maps-platform/terms)

## The Unreal feature set to center the whole system around

If the question is "which Unreal capabilities should ALIS bet on so it does not repaint the same wall three times," the answer is fairly clear.

**Bet heavily on World Partition.** Epic's current docs describe it as a single persistent level subdivided into streamable grid cells loaded by streaming sources, and ALIS's own `ProjectWorld` docs already layer tiles and world-data logic on top of that. This is the safest future-proof direction because it follows Epic's world architecture instead of inventing a competing partition system. [[20]](https://dev.epicgames.com/documentation/unreal-engine/world-partition-in-unreal-engine)

**Bet heavily on PCG.** Epic now documents PCG generation modes specifically for larger worlds, including partitioned, hierarchical, and runtime generation. ALIS should treat PCG graphs as the "morphogenesis engine" that turns tile DNA into visible reality. [[21]](https://dev.epicgames.com/documentation/unreal-engine/using-pcg-generation-modes-in-unreal-engine)

**Use Georeferencing from the start.** It lets Unreal express real geographic coordinates such as lat/long or UTM once the environment is georeferenced, which matters if ALIS wants real-world ingestion and repeatable server-side tile pipelines instead of ad hoc scene coordinates. [[22]](https://dev.epicgames.com/documentation/unreal-engine/georeferencing-a-level-in-unreal-engine)

**Use Geometry Script and Shape Grammar together.** Geometry Script gives procedural mesh editing/generation through Blueprints and Python, while Shape Grammar gives rules/modules for structured procedural content. Shape Grammar handles a lot of the "lego DNA" logic for facades and shells; Geometry Script covers the cases where you need custom mesh derivation, boolean work, footprint cleanup, or generated roof/interior utility geometry. [[23]](https://dev.epicgames.com/documentation/unreal-engine/geometry-scripting-users-guide-in-unreal-engine)

**Use Landscape import, splines, and RVT instead of custom terrain tech unless profiling forces otherwise.** Landscape already understands large heightmaps and road-conforming spline deformation; RVT is designed for large-area landscape shading and works well with splines and decal-like blending. That is enough power for the first serious ALIS world-generation system. [[24]](https://dev.epicgames.com/documentation/unreal-engine/landscape-technical-guide-in-unreal-engine)

**Prefer Nanite plus streaming over giant HLOD proxy pipelines for the endless-world case.** Nanite is designed for fine-grained streaming and automatic LOD over high-detail meshes. ALIS's own docs are already skeptical of HLOD for endless or constantly changing worlds because of proxy asset explosion and rebuild cost. I think ALIS should keep that stance unless profiling on a fixed hero district proves otherwise. [[25]](https://dev.epicgames.com/documentation/unreal-engine/nanite-virtualized-geometry-in-unreal-engine)

**Exploit OFPA and commandlets for collaboration and regeneration.** One File Per Actor is enabled by default with World Partition, which helps actor-level source control and regeneration workflows. For ALIS that means automated world realization can remain incremental and contributor-friendly instead of becoming a monolithic binary asset nightmare. [[26]](https://dev.epicgames.com/documentation/unreal-engine/one-file-per-actor-in-unreal-engine)

## How agentic support should be wired into ALIS

The right agentic model for ALIS is **multi-agent, schema-first, and tool-mediated**.

At the protocol level, MCP is now a real advantage because it is an open standard for connecting AI applications to external systems, tools, and workflows, with broad ecosystem support across assistants and developer tools. That makes it a strong foundation for an ALIS toolchain that should not be trapped inside one vendor or one IDE. [[27]](https://modelcontextprotocol.io/docs/getting-started/intro)

On the Claude side, Claude Code skills are now a mature fit for repeatable repository and workflow knowledge. Anthropic's docs describe skills as `SKILL.md`-based reusable procedures that load only when needed, can be auto-invoked when relevant, follow the Agent Skills open standard, and support things like invocation control, subagent execution, and dynamic context injection. That is almost exactly what ALIS needs for tasks like "normalize Overture buildings into tile JSON," "validate tile schema," "review PCG graph diffs," or "run world builders for changed tiles." [[28]](https://docs.anthropic.com/en/docs/claude-code/skills)

On the OpenAI side, Codex is now explicitly positioned as the software-development surface, while Work is for longer research/deliverables. OpenAI's current plugin system packages reusable workflows from skills, apps, and app templates, and plugins can bundle skills and even MCP server configurations for Codex and ChatGPT. For ALIS, that means a reproducible "world generation plugin" can eventually bundle repo-local skills, approved apps, and MCP access patterns instead of relying on each contributor to hand-assemble the same environment. [[29]](https://help.openai.com/en/articles/20001256-plugins-in-codex)

Inside Unreal, the new development is especially important: Epic now ships an experimental Unreal MCP plugin, and UE 5.8 release notes call out a new experimental MCP plugin for Unreal Editor. Epic's docs say the plugin runs inside the editor process, accepts connections only from the same machine by default, has no authentication layer, is not designed for remote use, and serializes tool invocations onto the game thread. Epic also now documents a dedicated PCG-and-LLMs workflow using Unreal MCP, with PCG-specific toolsets. That means "agent edits Unreal through a controlled tool API" is no longer hypothetical. It is becoming first-class enough to design around, though still carefully because it is experimental. [[30]](https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-5-8-release-notes)

So the ALIS agent architecture should be split into roles.

A **Scout agent** acquires and catalogs raw data sources into STAC/GeoParquet/COG form, checks source licenses, and updates manifests. A **Cartographer agent** normalizes raw sources into ALIS tile JSON and produces diffs. A **Genome agent** converts footprints, roads, and zoning into archetype-level building and biome DNA. An **Unreal Builder agent** uses commandlets and Unreal MCP to regenerate DataAssets, PCG outputs, and realization layers for changed tiles only. A **Validator agent** checks schema correctness, overlaps, asset references, partition alignment, and perf budgets before anything lands. This division is an inference from the capabilities documented by ALIS, Unreal MCP, Claude skills, and Codex plugins, but it is the cleanest way to keep the system deterministic and reviewable. [[31]](https://github.com/<user>/alis/blob/main/Plugins/Editor/ProjectDefinitionGenerator/README.md)

The most important rule is that agents should usually edit **schemas, attributes, and presets**, not raw Unreal scenes. ALIS's own docs already say agents are good at structured text with clear fields and bad at raw mesh reasoning. Unreal's own MCP docs also imply you should be careful because tool calls are serialized on the main editor thread and the plugin is local/editor-bound. So the best use of agents is to produce deterministic edits to tile JSON, PCG parameters, and generation settings, then let Unreal rebuild from there. [[32]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

One more feature is worth adopting early: Unreal's experimental Semantic Search plugin adds AI search to the Content Browser and ranks by visual/contextual meaning rather than literal asset names. For a large open project with many generated assets and kit pieces, that could become a very useful "human plus agent" retrieval layer inside the editor, especially once ALIS accumulates many modular building parts and material variants. [[33]](https://dev.epicgames.com/documentation/unreal-engine/semantic-search-in-unreal-enigne?lang=en-US)

## The phased path that makes the most sense

The first breakthrough ALIS should chase is **not** full city reconstruction. It is a convincing **tile pipeline** that proves the architecture. The first serious milestone should ingest one real area from open sources, georeference it, generate continuous terrain from a base height source, realize roads from vector centerlines, generate block-level building massing from footprints, and layer biome/zone-driven PCG detail on top. If that works cleanly through JSON and commandlets, the foundation is correct. [[34]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

The next milestone should be **building DNA**. That means replacing "just extruded footprints" with archetype-driven building families using shape grammar, modular shell kits, facade rules, entrances, roof grammars, and interior presets. This is the point where ALIS starts to look mind-blowing rather than merely technically competent, because the world stops being imported GIS and starts becoming a living, systemic reconstruction. [[35]](https://dev.epicgames.com/documentation/unreal-engine/using-shape-grammar-with-pcg-in-unreal-engine)

The third milestone should be **streamed world intelligence**. At that point, tiles should no longer be static generated chunks only. The server should be able to deliver tile manifests, source revisions, event overlays, and seed changes so that a place can remain the same place while still evolving. ALIS's own data layer and event model already points that way, because buildings and layers can participate in events like blackout or shelling. That is where the "real world, but alive" thesis becomes stronger than a simple digital twin. [[36]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

## The main risks to avoid

The biggest architectural trap is building a **custom partition and streaming system** in parallel with World Partition. ALIS's own docs already argue against that, and Epic's world architecture has only become more committed to World Partition, OFPA, Data Layers, and builder automation. Competing with that stack would cost a lot and age badly. [[37]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

The next trap is turning JSON into a giant scene graph of prop transforms. ALIS already warns against exactly that, and it is right. Data should define semantics and constraints; generators should handle repeated realization. Otherwise you get the worst of both worlds: hard-to-author schemas and brittle generated content. [[4]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)

Another trap is making Cesium, photogrammetry, or any one external source the **core identity** of the system. Cesium is excellent as an adapter; photogrammetry is excellent for hero zones; Overture and OSM are excellent map foundations. But ALIS should remain source-agnostic at the canonical tile layer so it can switch providers, merge municipal datasets, or replace weak regions over time without rewriting the runtime architecture. [[38]](https://github.com/CesiumGS/cesium-unreal)

There is also a real operational risk with Unreal MCP. Epic explicitly says it is local-only by default, unauthenticated, and not designed for remote use. So ALIS should treat it as a workstation-local or locked build-node tool, never as a public service. If remote orchestration is needed later, the safe pattern is to wrap it behind your own authenticated control plane rather than exposing the editor plugin directly. [[39]](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor)

## Final recommendation

The strongest long-term move for ALIS is to define a **world genome standard** and then let everything else orbit it.

That standard should be tile-based, georeferenced, deterministic, and gameplay-aware. It should ingest open geospatial data such as Overture, OSM, Copernicus DEM, and local open LiDAR where possible. It should live outside Unreal in open formats and object storage. It should generate Unreal-facing DataAssets and realization layers incrementally through ALIS's existing generator patterns. And it should drive World Partition, Landscape, PCG, Geometry Script, Shape Grammar, Nanite, RVT, and Data Layers instead of bypassing them. [[40]](https://docs.overturemaps.org/guides/transportation/)

If ALIS does that, the project does not become "an Unreal scene of a city." It becomes a **regenerable world organism**: terrain, roads, buildings, biomes, events, and gameplay capabilities all grow from open data plus ALIS's own semantic rules. That is the design most likely to be fast to prototype, hard to obsolete, contributor-friendly, legally safe for open source, and impressive enough to feel like a genuine step beyond normal open-world workflows. [[41]](https://github.com/<user>/alis/blob/main/Plugins/World/ProjectWorld/README.md)
